xcrawl

一个以策略边界为第一原则的静态网页爬虫。遍历、抓取和资源管控在这里完成；页面解析、链接发现与可读性提取委托给 readabilities-rs。本文用五张图建立五分钟系统地图。

01 · 产品介绍

xcrawl 是一个策略先行的单进程网页爬虫。它把「不越过配置边界」放在性能和覆盖面之前——在发出任何一次 HTTP 请求之前，依次经过 URL 校验、全局预算预留、源站速率许可和 CIDR 地址过滤，六道关口全过才真正发请求。 1

换个视角 把 crawler 想成「审计过的抓取预算器」：每一次网络动作都先记账、再执行。即使目标站返回了意料之外的内容，消耗也不会越过配置上限。

它面向需要受控采集的场景——你知道要爬哪个站、要多少页、愿意花多少带宽，剩下的交给它：默认只爬种子 URL 的同站路径，深度和页数都有上限，robots.txt 按 RFC 9309 处理，私有地址和非标端口默认拒绝。

输出有两种形态：流式 JSON Lines 逐行吐出页面、失败、请求事件和最终摘要，不需要在内存里保留整个抓取结果；收集模式把结果聚合为一份完整的 CrawlReport。两种形态共享同一套抓取内核。

它不是什么
xcrawl 不做浏览器渲染、不绕 WAF、不做分布式持久化、不下载文档类资源，也不绑定任何 REST 或 MCP 接口。这些能力属于外部系统，它只负责把拿到的响应体原封不动传给分析器。

02 · 功能与特性

八个核心能力覆盖了从配置校验到结果交付的完整链路。每条特性止步于「读者知道有这能力、知道谁会用它」，运转机制留到后面的架构图与主走查里展开。

  • 策略分组配置 — 把参数按 traversal / scope / network / robots / retry / limits / output 七个维度分组，每组独立校验，冲突组合在启动前就拒绝。
  • 六道请求前校验 — 每次发请求前依次过 URL 格式、端口范围、作用域、全局预算、源站限流、CIDR 白黑名单，任一不通过即取消。
  • 单跳传输模型 — 关闭 reqwest 内置重定向，每一跳手动发起、手动校验目标、手动统计消耗，重定向不绕过作用域检查。
  • RFC 9309 robots — 支持 product-token 分组、`*` 和 `$` 通配、百分号归一化、Crawl-delay 上限；4xx 视为不可用（允许抓取），5xx 视为不可达（禁止抓取）。
  • 自适应源站调度 — 每个 origin 独立维护下一次可发时间、in-flight 信号量、robots delay 和 Retry-After 截止时间，支持 429/5xx 后指数退避。
  • 可插拔页面分析 — 通过 PageAnalyzer trait 接入，默认实现委托给 readabilities-rs；分析跑在 Tokio 阻塞池上，不占用网络并发槽位。
  • 双模式输出 — crawl() 收集完整报告，crawl_with_sink() 以流式 CrawlRecord 推送，后者不需要把页面驻留内存。
  • Frontier 可替换 — Frontier trait 封装去重与入队语义，默认内存实现提供 BFS/DFS 两种策略；自定义实现可接入外部存储。

04 · 系统上下文

xcrawl 坐在调用者和目标网站之间，左接命令或库调用，右连 HTTP 网络。页面分析这一步委托给外部 crate readabilities-rs，它本身不做任何 HTML 解析。

图解。四个外部角色环绕中心的 xcrawl：
  • 调用者通过 CLI 或库 API 进入，提供种子 URL 和策略配置；库模式下还可以注入自定义 Frontier 和 CrawlSink。
  • 目标网站是纯 HTTP 交互对象，xcrawl 关闭重定向后每一跳手动发起，保证作用域校验不会被绕过。
  • readabilities-rs是可替换的分析后端，xcrawl 只传原始响应字节，不持有任何 DOM 或解析逻辑。
  • 输出接收方默认是标准输出（JSON Lines），也可以是实现了 CrawlSink trait 的任意结构体。
一条关键路径：调用者 → 配置校验 → 抓取循环 → 单跳请求 → 分析器 → 记录输出。注意，robots.txt 请求也走同一套单跳传输，不会绕过预算和限流。

05 · 架构分层

内部划分为五层，自上而下依赖方向严格一致。上层调用下层，下层不感知上层。策略与配置在最顶部，执行内核在中间，传输与分析在最底部。

分层职责。
  • 入口层负责把 CLI 参数或库调用翻译成 CrawlConfig，在进入主循环前完成配置校验。它不参与任何网络动作。
  • 编排层是 Crawler::run 的主循环：从 Frontier 出队、管理并发 FuturesUnordered、处理成功失败、把新发现链接重新入队、向 sink 推送记录。
  • 策略控制层是抓取的守门人：预算检查扣减、源站限流排队、robots.txt 规则判定、作用域匹配。任何请求都必须先过这一层。
  • 传输层只做一件事：发出一单跳 HTTP 请求并返回结果（或重定向位置）。内嵌 CIDR 校验的 DNS 解析器，阻止 SSRF 类攻击。
  • 分析层是 trait 边界，默认实现把原始字节丢给 readabilities-rs，跑在阻塞线程池上，不占网络并发槽。
容易混淆的是「策略控制」和「传输」：策略决定能不能发，传输负责怎么发。两者之间是单向调用——传输层从不反查策略。

06 · 主走查：单页抓取全流程

拿一个 frontier 中的 URL，走完从出队到产出 CrawlPage 的六步。这是 xcrawl 最核心的执行路径，所有策略控制点都在这条线上。

  1. 出队与预算预检 — 主循环从 Frontier 取出下一条 FrontierEntry，先检查全局预算（页数、HTTP 请求数、deadline）是否还有余量，不满足则直接标记终止。
  2. 获取源站许可 — 向 OriginScheduler 申请该源站的 in-flight 信号量和下一次可发时间，必要时 sleep 等待。robots.txt 的 Crawl-delay 和 Retry-After 也在这里合并进等待时间。
  3. robots 判定 — 该源站的 robots 状态若未拉取，先异步发起一次 robots.txt 请求（同样走单跳传输 + 预算），然后用 user-agent 匹配规则，不允许则返回 robots 拒绝失败。
  4. 单跳请求 — OneHopTransport::send_one_hop 发起 HTTP GET，先做 URL/端口/CIDR 校验，再流式下载并逐块扣减字节预算。遇到 3xx 返回重定向位置而非自动跟随。
  5. 重定向处理 — 若收到重定向，对目标 URL 重做作用域检查和预算预留，递归最多 max_redirects 跳。HTTPS → HTTP 降级默认拒绝。
  6. 分析与发现 — 把最终响应体以 move 方式传给 PageAnalyzer（在阻塞池执行），得到文章内容、链接、元数据；链接经过 scope/depth/nofollow 过滤后批量回注 Frontier。
为什么是单跳而不是自动重定向？
reqwest 的内置重定向会跳过作用域检查、robots 判定和预算计费。手动处理每一跳，才能保证「每次实际网络动作都先审计」这个核心不变量不被绕过。代价是代码量增加——但这是有意的取舍。

07 · 模块结构与依赖

十一个源文件，核心是 crawler.rs（占 30%）。依赖关系从外向内收束：main.rs 只依赖公共 API，crawler.rs 协调全部内部模块，fetch.rs 和 analyzer.rs 是两个与外部系统对接的边界。

依赖方向。图中箭头表示「使用 / 依赖」关系，从上到下、从边到心收束到 crawler.rs：
  • config.rs 和 model.rs 是纯数据层，几乎不依赖其他模块，被全库引用。
  • 左侧四个策略模块（budget / throttle / robots / frontier）各管一类约束，被 crawler 调用，彼此之间不直接依赖。
  • 右侧 fetch.rs 和 analyzer.rs 是两个边界模块——前者对接网络，后者对接外部分析 crate。
  • lib.rs 做公共 API 的再导出，main.rs 只调公共 API。
这种「中心协调 + 四周能力」的布局让替换单个能力（比如换一个持久化 Frontier）不影响其他模块。

08 · 核心数据流

数据从 URL 入队开始，经过抓取和分析，最终以 CrawlRecord 流出。整条链路上有两个分叉点：重定向（回到抓取起点）和失败（直接输出 Failure 记录）。

数据流主线。蓝色粒子沿主路径运动，展示一次成功抓取的完整数据流转：
  • 入口：FrontierEntry（URL + depth）从队列出来，这是每一页的起点。
  • 三道闸：策略预检 → robots 判定 → 单跳传输，任一环节不通过就转向失败路径。
  • 核心转换：HTTP 响应体 → PageInput → PageAnalysis，数据形态从原始字节变成结构化的文章和链接。
  • 两个出口：成功产出 CrawlPage + 链接回注；失败产出 CrawlFailure，两者都是 CrawlRecord 的变体。
  • 闭环：新发现的链接经过 scope 和 depth 过滤后回注 Frontier，驱动抓取持续推进。

09 · 策略与预算系统

这是 xcrawl 区别于普通爬虫的核心。预算不是简单的计数变量——它是一个在每次网络动作前都必须「先预约、后消费」的记账系统，任何环节的超额都会立即终止对应的动作。

策略分七层组织：遍历（怎么爬）、作用域（爬哪里）、网络（怎么连）、robots（守规矩）、重试（失败怎么办）、资源限制（花多少）、输出（长什么样）。每一层都有独立的默认值和校验逻辑。 2

核对处 七个策略分组对应 config.rs 里的七个 struct：TraversalPolicy、ScopePolicy、NetworkPolicy、RobotsPolicy、RetryPolicy、ResourceLimits、OutputPolicy。
策略控制点。左侧是请求发出前必须通过的五道检查，右侧是支撑这些检查的四个策略实体：
  • URL 校验：格式合法性、端口是否在允许列表、URL 长度是否超限。这是最便宜的检查，最先做。
  • 作用域匹配：按 origin / domain / any 三级判定，再叠加路径前缀的 include/exclude。重定向目标也走这一步。
  • 全局预算：CrawlBudget 维护 HTTP 请求数、下载字节数、唯一 origin 数三个计数器，加上总 deadline。预约成功才继续。
  • 源站限流：OriginScheduler 用信号量限制 in-flight 并发，用时间戳维护下一次可发时间，合并 robots delay 和 Retry-After。
  • CIDR 过滤：在 DNS 解析阶段（ValidatingResolver）就验证解析出的 IP 不在拒绝列表里，从源头阻止 SSRF。
这些检查的排列顺序是「先便宜后昂贵」：计算量小的放在前面，涉及网络等待的放在后面。

10 · 架构特征与取舍

xcrawl 的设计选择偏向保守和可控，而不是最大吞吐。下面六个取舍反映了它「策略优先」的核心定位。

单跳传输 vs 自动重定向

关闭 reqwest 的重定向能力，手动处理每一跳。代价是代码量增加、需要自己维护重定向链；收益是重定向目标也必须过作用域、预算和 robots 检查，没有任何网络动作能绕过策略层。对于安全敏感的采集场景，这笔交易是划算的。

内存 Frontier vs 持久化队列

默认 InMemoryFrontier 全部放内存，结构简单、入队去重原子。代价是不能做大规模分布式抓取，也不能断点续爬；收益是接口极简、无外部依赖。需要持久化时通过 Frontier trait 注入自定义实现。

同步分析器 vs 异步分析器

PageAnalyzer trait 是同步的，分析跑在 Tokio 阻塞池上。代价是分析和网络共享同一套并发模型但不共享槽位，需要用户理解「网络并发 8 不等于总并发 8」；收益是 trait 简单，接 CPU 密集型解析库（如 html5ever 这类同步实现）不需要额外适配。

预算预扣 vs 事后结算

全局预算（请求数、字节、origin 数）在请求前预扣，失败不退回。代价是某些失败场景会浪费预算计数；收益是不会出现「已经发了请求才发现超预算」的竞态，预算上限是硬边界而不是软目标。

细粒度策略分组 vs 简单配置

配置按七个维度分组，每个维度有五到十个参数，CLI 暴露三十多个 flag。代价是新用户上手有学习成本，参数之间可能有冲突；收益是每个约束都可以独立调节，配置冲突在启动时就能被 validate() 捕获。

流式输出 vs 全量收集

提供两种使用模式：crawl_with_sink 流式推送、crawl 收集报告。代价是内部多了一层 CrawlSink 抽象和 emit 状态管理；收益是大批量抓取不需要把所有页面驻留内存，输出字节也有预算上限。
